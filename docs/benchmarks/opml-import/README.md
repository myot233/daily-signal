# OPML 导入性能

2026-09-27，在 Apple Silicon macOS 上用一份真实的 93 个订阅（约 20 KiB，其中 45 个来自 GitHub）的 OPML 测量。订阅地址、原始响应和用户数据库不随仓库发布。

## 结果

同一批已录制的 RSS 响应、错误和逐请求等待时间，在独立空数据库中分别执行三次；保留原始等待时间，包括超时。完整结果见 [full-replay-results.json](./full-replay-results.json)。

| 指标                 |         原实现 |      优化后 |
| -------------------- | -------------: | ----------: |
| 全部抓取结束，中位数 |     100.741 秒 |   59.660 秒 |
| 尝试抓取速率         |    0.923 个/秒 | 1.559 个/秒 |
| 保存订阅列表，中位数 | 与抓取一起返回 |  5.215 毫秒 |
| 保存的订阅           |             82 |          93 |
| 成功抓取 / 失败      |        82 / 11 |     82 / 11 |
| 保存文章             |          6,150 |       6,150 |

完整抓取耗时减少 **40.8%**，吞吐量提高 **68.9%**。三轮中成功订阅与文章内容的指纹一致；优化后另外保留抓取失败的订阅，方便重试。订阅列表保存耗时范围为 5–46 毫秒，不含 HTTP 和界面开销。这只是导入确认时间，不能当作所有文章已经抓取完成。

另在打包后的 Tauri 应用中通过原生文件选择器导入同一文件，实网后台抓取用时 **65.54 秒**，得到 6,107 篇文章，12 个源失败。实网内容、缓存和网络状态会变化，该次结果用于验证端到端流程，不用于证明内容一致或精确加速比。

## 改动与约束

- 订阅元数据一次事务保存，后台抓取进度独立查询，界面无需等待所有站点返回。
- 全局最多 8 个请求，同一主机最多 4 个；排队时允许其他主机先执行，避免同一站点占住队列。
- 保留原来的请求超时、响应大小限制、公共地址验证及重定向保护。
- 失败订阅保持可见；重复导入不生成重复订阅，进行中的导入/刷新不能重复启动。
- 进度在当前进程内保存；重启后可以手动刷新已保存的订阅。

试过每个主机最多 2 个请求，完整回放需约 105.6 秒；该样本集中有较多同站点订阅，因此没有采用。

这些结果是单机、单份订阅集合的测量。回放隔离了上游网络波动，但不是通用网络性能保证，也不是 AI 内容质量 benchmark。可用自己的 OPML、独立数据库和相同响应/延迟记录重复比较；仓库中的服务测试覆盖导入去重、安全限制、并发上限、调度公平性和后台任务状态。
